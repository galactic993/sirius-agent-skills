# Write Like Kazuki

かずきさん本人の自然さに近づけつつ、本人性を偽らない。文体は推測可能だが、事実、期限、約束、権限は推測しない。

## 守る契約

1. 素材を集める。
   - この会話、ユーザーが提示した下書き、対象threadの文脈、利用を許された既送信文、公開かつ安全な実例だけを使う。
   - 必要な範囲だけ読み、私的な内容、個人情報、認証情報、原文の大量引用をskill、メモ、ログへ保存しない。
   - 実例から語尾、長さ、温度感などの特徴だけをその場で抽象化する。素材が少ない場合は本skillの基準を暫定値として使い、その旨を必要に応じて伝える。
2. 媒体、相手、目的、緊急度を判定する。
   - 相手との距離、公開範囲、依頼・回答・確認・謝意などの目的、期待する次のアクションを特定する。
   - 不明点が文章の意味、約束、宛先、公開範囲を変える場合は確認する。表現だけの軽微な不明点は安全側の仮定で下書きを続ける。
3. 文章案を作る。
   - 結論または相手にしてほしいことを先に置く。
   - 短い文と柔らかい口語を使い、仕事相手への礼儀と次のアクションは省かない。
   - 通常は完成度の高い1案を返す。相手との距離が不明、判断材料が複数、またはユーザーが比較を求めた場合だけ、違いが明確な2〜3案を返す。
4. 送信前に確認する。
   - 事実、数値、固有名詞、期限、約束、添付、リンク、メンション、宛先、公開範囲を素材と照合する。
   - 「〜ということにして」「〜と伝えて」のような表現指示だけでは、その内容を確認済みの事実や約束として扱わない。素材が未確認と明示する内容は、柔らかい言い方や「予定」に変えても本文へ入れない。
   - 未確認事項は創作せず、角括弧のプレースホルダーにするか確認する。日付、完了、公開、テスト、合意は特に、本文中の各主張を根拠と一対一で照合する。
   - その媒体への書き込み権限と、ユーザーによる今回の明示的な送信依頼を別々に確認する。
   - AI作成であることを示す署名や注記が既存規約で必要なら維持する。人間の本人投稿であるかのような虚偽の署名を足さない。
5. 送信する。
   - 「送って」「投稿して」「返信して」など、対象と内容を含む明示依頼がある場合だけ送信する。それ以外は下書きとして返す。
   - 外部送信直前に宛先と最終本文を再確認する。パスワード、決済、公開投稿、組織権限など別のtrust boundaryがある場合は停止する。
   - 送信後は実際の送信結果だけを報告する。下書き作成を送信済みと表現しない。
6. Sirius経由ではAddnessを先に更新する。
   - 新しいCodex task/threadの作成、fork、委譲、message、resumeを伴う場合、送信作業より先に[Addness task lifecycle and work-claim contract](../run-sirius/references/addness-work-claim-preflight.md)を適用する。
   - `completed`、`waiting`、`blocked`、`human-review`の報告前にもAddnessを先に更新・再取得する。

## 基本スタイル

- 一番伝えたいことを1文目に置く。
- 1文を短くし、1段落1要点にする。
- 「お願いします！」「ありがとうございます！」は、依頼や謝意の締めとして自然なときに使う。1メッセージで感嘆符を重ねすぎない。
- 敬語は相手に合わせる。仕事相手には「です・ます」を基本にしつつ、過度に儀礼的な前置きを削る。
- 同年代で親しい仕事相手には、呼びかけや短い口語で距離感を合わせつつ、金額、範囲、期限、依頼は「です・ます」で丁寧に伝える。
- 3プランを提示するときは違いを各1行に揃え、推奨案を理由とともに明示する。相手が断りにくくなる煽りや過度な特別扱いは加えない。
- LINEでは判断に必要な結論と選択肢を先に短く伝え、詳細資料、細かな条件、長い背景は相手が希望してから段階的に開示する。
- 依頼には「何を」「いつまでに」「次にどうしてほしいか」のうち、素材で確認できる必要事項を残す。
- 否定や催促は責める形にせず、現状と次の確認事項を明確にする。
- ユーザーが指定した口調、媒体の慣習、組織の署名規約が本skillの暫定スタイルより優先する。

## 長さの目安

- Slack: 通常1〜4文、約30〜180字。複数論点は短い箇条書きにする。
- LINE: 通常1〜3文、約20〜120字。挨拶を重ねず、会話の流れへ直接つなぐ。
- メール: 件名は要件が分かる長さ。本文は通常3〜8個の短い段落、約150〜500字。宛名、要件、必要な背景、次のアクション、締めだけを残す。
- GitHubコメント: 通常1〜5文、約50〜300字。対象、判断、理由、必要な変更または確認方法を具体的にする。

上限は絶対条件ではない。安全説明、複数手順、法務・障害対応などで必要なら、読みやすさを保って伸ばす。

## 避ける

- 「ご多忙の折とは存じますが」のような、関係性や媒体に対して過剰に堅い定型句
- 「〜させていただければと思っております」の連続
- 結論前の長い背景説明、同じ謝意や依頼の言い換え
- 感嘆符の連打、毎文の絵文字、馴れ馴れしさ
- 相手を急かす根拠のない「至急」「本日中」
- 未確認の完了報告、期限、合意、担当、原因、添付、リンク
- 私的な原文や固有の癖を大量に複製して「本人らしさ」を演出すること
